# ADR-003: 利用組織・利用者・ロール・職位を、共通の organization モジュールに置く

**Status:** Accepted
**Date:** 2026-11-11
**Requirements:** NFR-010, NFR-011, NFR-007, NFR-013

## Context

- 承認ワークフロー(`workflow`、ADR-002)は、承認者を決めるために、利用組織・利用者・職位を必要とする。業務側も、利用組織・利用者・ロールを必要とする(FR-001〜FR-005)。
- `workflow` は、将来、汎用のワークフロー SaaS として切り出す(NFR-010)。業務モジュールには依存できない。
- 利用組織・利用者・ロール・職位は、シンジケートローンの知識を含まない。シンジケートローン固有なのは、融資案件ごとの立場(リード銀行か出資者か)だけである。
- 利用組織はテナントの単位であり、他の組織のデータを見せない(NFR-007)。
- ID プロバイダは差し替えられるようにする(NFR-013)。
- モジュール間の依存は構造テストで検査する(NFR-011、C-009)。

## Decision

- 利用組織・利用者・ロール・職位を、Spring Modulith のモジュール `organization` に置く。
- `organization` は、他のどのモジュールにも依存しない。シンジケートローンの用語・データを持ち込まない。
- `workflow` と業務モジュールは、どちらも `organization` の公開 API を使う。組織・職位のデータを複製しない。
- 融資案件ごとの立場(リード銀行・出資者)は、`organization` ではなく業務モジュールが持つ。
- ID プロバイダからは利用者の識別だけを受け取り、ロールと職位は `organization` が持つ。
- SaaS として切り出すときは、`workflow` と `organization` を一緒に持ち出す。
- 以上の依存の規則は、構造テスト(Spring Modulith と ArchUnit)で検査する。

## Consequences

- 良い点: 組織・職位の正が1つになり、同期が要らない。
- 良い点: ロールと職位を ID プロバイダに持たせないので、ID プロバイダを差し替えても移す必要がない。
- 注意点: `workflow` の依存先が、「なし」ではなく「`organization` だけ」になる。`organization` にローンの知識が入らないことを、構造テストで守る必要がある。
- 注意点: SaaS では、`organization` を顧客の組織情報とつなぐ方法(取り込みや連携)が別に必要になる。
- **Alternatives considered:**
  - `workflow` が組織・職位を持ち、業務側と同期する — 二重管理になり、同期のずれと取りこぼしへの対策が要る。
  - `workflow` は承認者を引くポートだけを定義し、業務側のアダプタが実装する — 正は1つで同期も要らないが、組織・職位は業務側に置かれ、SaaS にするときにディレクトリの実装を別に作る必要がある。もともと汎用の組織・職位を、業務側に置く理由がない。
  - ID プロバイダに職位を持たせる — 本システムでは管理しなくて済むが、ID プロバイダを差し替えると職位も移す必要がある(NFR-013)。簡易な自作の ID プロバイダでは負担が大きい。
