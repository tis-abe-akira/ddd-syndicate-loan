# ADR-002: 承認ワークフローを、業務から独立した workflow モジュールにする

**Status:** Accepted
**Date:** 2026-11-11
**Requirements:** NFR-010, NFR-011, NFR-007, NFR-014

## Context

- 承認ワークフロー(稟議)は、将来、汎用のワークフロー SaaS として切り出して販売する(NFR-010)。そのため、シンジケートローンの用語・データに依存してはならない。
- 稟議にかける業務は、借り手審査・出資者審査・シンジケートへの呼びかけ・ファシリティ組成・参加の回答・ドローダウンへの拠出の回答と多い(docs/brief/06-actors-and-roles.md)。業務ごとに承認の仕組みを作ると、規則(合議・メイントラック・差し戻し・否決・再起案)が散らばる。
- 稟議は利用組織の中で閉じ、他社の稟議は見えない(NFR-007)。SaaS のテナント分離も同じ要求になる。
- モジュール間の依存は構造テストで検査する(NFR-011、C-009)。依存の向きを決めておけば、構造テストで守れる。
- 組織・利用者・ロール・職位の持ち主は、ADR-003 で決める。

## Decision

- 承認ワークフローを、Spring Modulith のモジュール `workflow` として作る。
- `workflow` は、業務モジュール(party・syndicate・facility・loan・fee・transaction)のどれにも依存しない。依存してよいのは、ADR-003 の `organization` モジュールだけとする。
- 業務モジュールは、`workflow` の公開 API(Spring Modulith の named interface)だけを使って稟議を申請・照会する。
- 承認の結果(承認済・否決・差し戻し)は、`workflow` が公開イベントとして出し、業務モジュールが購読して業務の処理をする。`workflow` は業務のコードを呼び返さない。
- 稟議の対象は、`workflow` から見て不透明な参照(種類と ID の文字列)で持つ。
- 承認経路を決める入力(金額、クレジットスコアなど)は、業務側が経路属性として値で渡す。経路の規則は、組織ごとに `workflow` の中で設定する。
- 否決後の再起案の判定に使う条件は、業務側が値で渡し、`workflow` が前回の値と比べる。
- テナントは利用組織とし、`workflow` は他の組織の稟議を見せない。
- `workflow` のテーブルは専用のスキーマに置き、業務のテーブルへの外部キーを持たない。
- お知らせは、`workflow` のイベントを通知の仕組みが受けて送る。`workflow` は通知の手段を持たない。
- 以上の依存の規則は、構造テスト(Spring Modulith と ArchUnit)で検査する。

## Consequences

- 良い点: `workflow` を、`organization` と一緒に、コードとデータごと切り出せる。業務の変更が `workflow` に及ばない。
- 良い点: 稟議の規則が1か所にまとまり、どの業務の稟議も同じ規則で動く。
- 注意点: 業務側は、稟議の結果をイベントで受け取るため、処理が非同期になりうる。イベントの取りこぼしと二重処理への対策が必要になる。
- 注意点: 経路属性と条件を値で渡すため、稟議の種類ごとに「何を渡すか」を定義する必要がある(Issue #12 と関係)。
- **Alternatives considered:**
  - 業務モジュールごとに承認の状態を持つ — 規則が散らばり、切り出せない。NFR-010 を満たさない。
  - 最初から別のサービス(別プロセス)として作る — 切り出しは確実だが、単一の構成の今は運用とテストの負担が大きい。モジュールの境界を構造テストで守っておけば、後で分けられる。
